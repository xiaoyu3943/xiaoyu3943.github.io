七、乐观锁（Optimistic Locking）

7.1 核心 SQL

7.2 rowcount 的含义

rowcount 含义 处理
1 更新成功（version 未变） 继续
0 并发冲突（version 已被其他事务修改） 抛异常，回滚重试

7.3 乐观锁 vs 悲观锁 使用场景

锁类型 机制 优点 缺点 适用场景
行级锁 (FOR UPDATE) 读取时锁定行 强一致性 阻塞等待 转账第一步：防止读到脏数据
乐观锁 (version) 更新时检查版本号 不阻塞 冲突时需重试 更新余额：兜底检测并发冲突

本项目同时使用两种锁：FOR UPDATE 确保读到的余额是准确的；version 作为兜底，防止 FOR UPDATE 之后的并发覆盖。

八、db.flush() vs db.commit()

操作 效果 可见范围
db.flush() 将 SQL 发送到数据库，不提交 当前事务可见、其他事务不可见
db.commit() 提交事务，永久写入 所有事务可见

flush() 让你在同一事务中写入 + 后续读到刚写入的数据，但不对外可见。所有操作最终由 get_db 统一 commit。

九、事务管理的”不提交原则”

原则 说明
业务代码不提交 服务层只做业务逻辑，不管理事务
依赖注入管事务 get_db 统一 commit/rollback
全或无 任何一步失败 → 全部回滚

十、确保的保证

保证 实现方式
✅ 幂等性 idempotency_key UNIQUE + 业务前先查
✅ 原子性 依赖注入统一 commit/rollback，全或无
✅ 一致性 出账扣款 + 入账加款 必定同时完成或同时回滚
✅ 隔离性 行级锁 (FOR UPDATE) + 乐观锁 (version)
✅ 死锁预防 按 ID 排序锁定，打破循环等待

十三、HTTP 状态码选择原则

异常 状态码 原因
AccountNotFoundError 404 资源不存在（语义正确）
InsufficientBalanceError 422 请求格式正确，但业务逻辑不允许
AccountFrozenError 422 同上，属于”不可处理的实体”
DuplicateIdempotencyError 409 请求冲突（重复提交）

422 vs 400：400 是”请求格式错误”（如 JSON 格式不对、必填字段缺失），422 是”请求格式正确但语义有问题”（如余额不足、账户冻结）。

十四、为什么要自定义异常？

优势 说明
自带 HTTP 状态码 无需在路由中手动判断和设置
统一响应格式 全局异常处理器统一转换
前端可区分处理 根据 code 展示不同 UI（弹窗、跳转、重试）
便于监控告警 日志系统可按 code 分类统计和告警
调用链清晰 抛出异常即终止，不需要层层返回错误码

十六、异常处理映射

异常 状态码 触发条件

十七、错误码规范建议

前缀 类别 示例

命名原则：大写 + 下划线分隔，语义明确，前端可直接 switch/case。

十八、核心要点速查

要点 实现
